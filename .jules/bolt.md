## 2025-05-18 - High-Frequency Directory Scans in Agent Watch Loop
**Learning:** `_watch_loop` periodically checks for newest and latest conversations every 0.3s. Using `Path.iterdir()` repeatedly constructs multiple `Path` objects per candidate directory on each tick, and re-checking filesystem birthtime/ctime across all session directories triggers repeated `os.stat` calls for immutable session creation times. Switching to `os.scandir` with `os.path` operations and caching session creation timestamps yields a ~2.5x to 6x speedup during conversation discovery.
**Action:** In watch loop and polling operations, avoid instantiating `Path` objects or issuing multiple `stat()` calls per item unless timestamps or sizes have actually changed; cache immutable metadata (like session ctime) per session ID.

## 2026-11-04 - Linear Approval Scans in Conversation Summaries
**Learning:** `list_conversations()` builds summaries across all discovered transcripts on each session switch or drawer render. In `_summarize()`, testing `has_pending_approval` using `any(a.get("conversation_id") == cid ... for a in mgr._pending_approvals.values())` created an O(N * M) nested scan over approvals for every conversation. Precomputing a set of conversation IDs with active pending approvals turns this into an O(1) set membership test, speeding up the pending check by ~9.5x - 17x.
**Action:** When computing per-entity flags against collection-wide stores (like approvals or locks) inside loops or frequent summaries, precompute set indices once rather than performing linear scans per item.

## 2026-11-12 - pyte Screen Display Traversal Overhead in Terminal Mirror Snapshots
**Learning:** `TerminalMirror.snapshot()` is called frequently across multiple endpoints (`/api/screen`, `/api/usage`, HUD polling, agent listing, and WebSocket requests). Every snapshot directly accessed `pyte.Screen.display`, which is an unmemoized property that re-renders all rows column by column, evaluating `wcwidth` on each character cell (1,920 character lookups per 24x80 snapshot taking ~1 ms per call), followed by regex parsing for mode and usage. Caching the rendered lines list and parsed mode/usage until the screen is mutated (`feed()` or `resize()`) provides a >40x speedup (reducing static snapshot time from ~1080 μs to ~1.4 μs).
**Action:** When working with terminal emulators or pyte screens, avoid evaluating `screen.display` on read-only queries or polling ticks unless the buffer has been marked dirty by input stream feeds or geometry resizes.

## 2026-11-13 - TmuxScreen Re-parses Mode and Usage on Every Snapshot
**Learning:** `TmuxScreen.snapshot()` is called on every `/api/screen`, `/api/usage`, and `get_usage_hud()` call. Unlike `TerminalMirror`, it had no cache for the parsed `mode` and `usage` fields. `parse_mode()` and `parse_context_and_usage()` each walk every screen line with multiple regexes (~24μs per 24x80 snapshot), and this parsing ran even when the pane content had not changed since the previous snapshot. `take_dirty_snapshot()` only deduplicated output *after* parsing, so the work was wasted on every unchanged poll. Caching parsed mode/usage keyed on the lines tuple, invalidated when `_refresh()` captures new content, cuts unchanged-snapshot time from ~26μs to ~1.6μs (~16x).
**Action:** Add `_cached_mode`, `_cached_usage`, and `_cached_lines_key` to `TmuxScreen`; return cached values when `tuple(lines)` matches the last key; invalidate on new content.
