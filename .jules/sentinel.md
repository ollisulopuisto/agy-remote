# Sentinel Security Journal

## 2026-11-07 - Agent Communication Disruption via Missing E2EE on Mailbox Mute/Unmute Endpoints
**Vulnerability:** When E2EE was enabled (`cfg.e2ee_enabled = True`), state mutation endpoints enforced encrypted envelopes and replay guards. However, `POST /api/mailbox/mute` and `DELETE /api/mailbox/mute` accepted unsealed JSON payloads with only token authorization, creating an encryption downgrade vulnerability and omitting replay protection. An attacker with token-only access (e.g. from network logs or plaintext LAN sniffing) could mute or unmute arbitrary agent-to-agent communication mailboxes or replay stale mute requests to disrupt multi-agent coordination without the E2EE key.
**Learning:** Inter-agent communication gating and mailbox controls directly impact agent coordination and execution flow. When an application supports an E2EE trust boundary, any REST endpoint modifying agent communication state must enforce payload encryption and replay guards just like prompt and tool execution endpoints.
**Prevention:** Strictly enforce encrypted envelope verification, decryption via `decrypt_payload`, and replay protection guards (`ReplayGuard`) across all mailbox control and agent communication endpoints whenever E2EE mode is enabled.

## 2026-11-06 - Prompt Execution Reordering Bypass via Missing E2EE on POST /api/sessions/{id}/queue/reorder
**Vulnerability:** When E2EE was enabled (`cfg.e2ee_enabled = True`), all content mutation and tool execution endpoints (`/api/prompt`, `/api/key`, `/api/sessions`, `/api/conversations/{id}/rename`, `/api/agents/jobs`, `/api/approvals/{id}/respond`, `/api/approvals/policy`, and WebSocket frames) enforced encrypted envelopes and rejected plaintext payloads with HTTP 400. However, `POST /api/sessions/{conversation_id}/queue/reorder` accepted unsealed JSON payloads with only token authorization, creating an encryption downgrade hole and lacking replay protection. An attacker with token-only access (e.g. sniffing local traffic or intercepting HTTP requests) could alter the execution order of queued user prompts or replay stale reorder frames to subvert prompt workflow without the E2EE key.
**Learning:** Any endpoint that influences the execution order of queued commands or prompts is part of the command execution lifecycle. When transport parity exists between WebSocket actions (which enforced envelope sealing) and REST fallback routes, omitting E2EE envelope decryption and replay validation on the REST route undermines the end-to-end encryption trust model.
**Prevention:** Strictly enforce encrypted envelope verification, decryption via `decrypt_payload`, and replay protection guards (`ReplayGuard`) across all session control and queue manipulation REST endpoints whenever E2EE mode is enabled.

## 2026-11-04 - Security Policy Downgrade via Missing E2EE on POST /api/approvals/policy
**Vulnerability:** When E2EE was enabled (`cfg.e2ee_enabled = True`), all content mutation and tool execution endpoints (`/api/prompt`, `/api/key`, `/api/sessions`, `/api/conversations/{id}/rename`, `/api/agents/jobs`, `/api/approvals/{id}/respond`, and WebSocket frames) enforced encrypted envelopes and rejected plaintext payloads with HTTP 400. However, `POST /api/approvals/policy` accepted unsealed JSON payloads with only token authorization, creating an encryption downgrade vulnerability and missing replay protection. An attacker possessing token-only access (e.g. from network logs or plaintext LAN traffic) could switch the server's approval policy to `auto_all`, thereby automatically permitting all future tool calls (including arbitrary command execution via `run_command`) without user confirmation and bypassing the E2EE approval gate.
**Learning:** Permission configuration endpoints that control automated tool execution policies are high-privilege authorization control planes. Allowing cleartext REST access to relax security policies creates an indirect authorization bypass on all downstream protected operations.
**Prevention:** Strictly enforce encrypted envelope verification, payload decryption (`decrypt_payload`), and replay protection guards (`ReplayGuard`) across all configuration endpoints that manage security permission models or tool gating policies whenever E2EE is enabled.

## 2026-11-03 - Unauthorized Tool Execution via Missing E2EE on POST /api/approvals/{approval_id}/respond
**Vulnerability:** When E2EE was enabled (`cfg.e2ee_enabled = True`), all content mutation endpoints (`/api/prompt`, `/api/key`, `/api/sessions`, `/api/conversations/{id}/rename`, `/api/agents/jobs`, and WebSocket frames) enforced encrypted envelopes and rejected plaintext payloads with HTTP 400. However, `POST /api/approvals/{approval_id}/respond` accepted bare JSON payloads with only token authorization, creating an encryption downgrade hole and missing replay protection. An attacker with token-only access (e.g. from network traffic or server logs) could approve dangerous tool calls, deny approvals, or inject altered tool arguments via `overwrite_args` without possessing the E2EE key.
**Learning:** Any endpoint that mutates execution state or grants security permissions must strictly align with the E2EE trust boundary. If WebSocket actions require encryption envelopes while corresponding REST endpoints accept plaintext JSON, the encryption boundary can be completely bypassed by downgrading to REST.
**Prevention:** Unconditionally enforce encrypted envelope validation, payload decryption with `decrypt_payload`, and replay protection using `ReplayGuard` on all state mutation and permission grant REST endpoints whenever E2EE mode is enabled.

## 2026-11-02 - Keystroke Injection via Missing E2EE Enforcement on POST /api/key
**Vulnerability:** When E2EE was enabled (`cfg.e2ee_enabled = True`), all content mutation endpoints (`/api/prompt`, `/api/sessions`, `/api/conversations/{id}/rename`, `/api/agents/jobs`, and WebSocket frames) enforced encrypted envelopes and rejected plaintext payloads with HTTP 400. However, `POST /api/key` directly accepted bare JSON payloads with only token authorization, creating an encryption downgrade hole that allowed an eavesdropper holding only the authentication token to inject keystrokes into live sessions without knowing the E2EE key.
**Learning:** Endpoints that execute actions or inject input into agent sessions must adhere uniformly to the encryption boundary. When an application provides alternate REST and WebSocket vectors for the same capability (`send_key`), partial E2EE enforcement on only one transport allows protocol downgrade attacks.
**Prevention:** Whenever E2EE mode is active, unconditionally gate all command and input injection endpoints with envelope verification, payload decryption (`decrypt_payload`), and replay protection guards (`ReplayGuard`).

## 2026-11-01 - Option Injection Hardening in Spawner Git Cloning
**Vulnerability:** Repository URLs and branch names supplied to the spawner (`POST /api/sessions`) could contain leading dashes or option injection strings (e.g., `ssh://-oProxyCommand=...`, `git@host:-oProxyCommand=...`, `--branch -u`). Although `--` was present before the URL, leading dashes in hostnames, scp paths, or branch parameters can trigger option injection in git or underlying ssh transport.
**Learning:** Git transport protocols (especially SSH and SCP-like syntax) interpret hostnames or paths beginning with `-` as command options for `ssh` (e.g., `-oProxyCommand=...`), potentially resulting in arbitrary code execution during clone operations.
**Prevention:** Strictly forbid leading dashes in repository URLs, extracted hostnames, SCP paths, and branch names in input validation routines before passing arguments to git.

## 2026-10-30 - Atomic Permissions on Uploaded Files
**Vulnerability:** In `/api/upload`, uploaded files were written with `open(dest, "wb")` and then tightened with `dest.chmod(0o600)`. Under standard umasks (e.g. 0o022), the file was created world/group readable (0o644) for a brief window before `chmod` ran, exposing potentially sensitive screenshots or uploaded images to other users on multi-user systems.
**Learning:** `open()-then-chmod` patterns suffer from a TOCTOU permissions race condition where files are created under the process umask before permissions are restricted.
**Prevention:** Always create sensitive files atomically with restricted modes at creation time using `os.open(path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)` and `os.fdopen()`, matching the secure file creation pattern used across this codebase for runtime tokens, VAPID keys, and certificates.
